    Discovery and JWKS¶

    Two documents describe the provider to whoever is about to talk to it. The discovery document says what the provider serves and where (OIDC Discovery 1.0 §3, RFC 8414 §2), and the JWK Set publishes the public keys a client verifies what it receives with and encrypts what it sends with (RFC 7517 §5). Both are read from what the provider is wired with: a grant, a client authentication method or an algorithm is announced because it is served, and stops being announced the moment it is not.

    The discovery document¶

    One document, served at the two places a client looks for it:

    Method Path Specification
    GET /.well-known/openid-configuration OIDC Discovery 1.0 §4
    GET /.well-known/oauth-authorization-server RFC 8414 §3

    Both answer 200, application/json, with Cache-Control: public, max-age=3600: a client may keep the document an hour.

    The routes are where the issuer says they are. OIDC Discovery 1.0 §4.1 appends the well-known path to the issuer, so the routes of the bundle are mounted under it: a deployment whose issuer is https://op.example.com serves https://op.example.com/.well-known/openid-configuration. Routes mounted anywhere else make every endpoint that locates the others fail at the first request, with an error that names both URLs, rather than publish endpoints a client would not find. RFC 8414 §3 inserts its well-known segment between the host and the path of the issuer instead: the two locations are the same URL under an issuer that is an origin, and under an issuer that carries a path, the route of the bundle answers under that path, which is not where RFC 8414 §3 looks.

    Every URL is built from the issuer, never from the Host header of the request that asked.

    What it publishes¶

    Each specification the provider implements contributes its own members, in the order they are wired, and nothing assembles a list of them beside the wiring. Two capabilities announcing the same member is a fault the provider refuses rather than arbitrates.

    Members What decides them
    issuer, authorization_endpoint, token_endpoint, userinfo_endpoint, jwks_uri The issuer, and the routes under it. Always present
    scopes_supported openid, the scopes the wired claims stand for, the scopes the clients of the tenant registered, and offline_access where a wired grant issues a refresh token and another spends one. Scopes and claims
    claims_supported, claims_parameter_supported sub and the claims the provider serves; true
    response_types_supported ["code"], and nothing else: no implicit flow and no hybrid
    response_modes_supported The response modes wired, query, form_post, query.jwt and form_post.jwt in the bundle, plus jwt when a signed mode is among them (JARM §2.1). Response modes
    grant_types_supported The grants the token endpoint is wired with, all seven in the bundle. Grants
    code_challenge_methods_supported The PKCE methods wired: S256. plain is wired nowhere
    acr_values_supported The classes of the policy of the tenant that the logins it serves can prove, in the order the policy names them. Tenants
    subject_types_supported The kinds of sub the provider assigns: public and pairwise. Pairwise subjects
    token_endpoint_auth_methods_supported, token_endpoint_auth_signing_alg_values_supported The client authentication methods wired, in the order they are tried, and what their assertions may be signed with. Client authentication
    id_token_signing_alg_values_supported, userinfo_signing_alg_values_supported The signature algorithms the provider is wired with: RS256, PS256, ES256 and EdDSA in the bundle
    id_token_encryption_*, userinfo_encryption_*, request_object_encryption_* (alg_values_supported, enc_values_supported) The encryption algorithms wired: ECDH-ES+A256KW and RSA-OAEP-256, with A256GCM. A deployment that wires no key encryption or no content encryption algorithm announces none of these pairs rather than empty lists
    request_parameter_supported, request_uri_parameter_supported, require_request_uri_registration true all three: a request_uri is read only from a URL its client registered
    request_object_signing_alg_values_supported The signature algorithms wired, and none beside them only when a client of the tenant registered request_object_signing_alg: none. Request objects
    authorization_response_iss_parameter_supported true: every authorization response carries iss (RFC 9207)
    pushed_authorization_request_endpoint, require_pushed_authorization_requests The endpoint; true only when every client registered for the tenant requires pushed requests. Pushed authorization requests
    device_authorization_endpoint The endpoint where a device code is asked for (RFC 8628 §4)
    introspection_endpoint, introspection_endpoint_auth_methods_supported, introspection_endpoint_auth_signing_alg_values_supported, introspection_signing_alg_values_supported The endpoint, the wired methods that authenticate a client (all but none), what their assertions are signed with, and the signature algorithms wired (RFC 9701). Introspection
    revocation_endpoint, revocation_endpoint_auth_methods_supported, revocation_endpoint_auth_signing_alg_values_supported The endpoint, and the methods of the token endpoint, none included
    end_session_endpoint, frontchannel_logout_supported, frontchannel_logout_session_supported, backchannel_logout_supported, backchannel_logout_session_supported The endpoint, and true for each logout channel wired, both in the bundle. Logout
    dpop_signing_alg_values_supported The signature algorithms wired. DPoP
    tls_client_certificate_bound_access_tokens true when a method that authenticates by certificate is wired, which the bundle does. Mutual TLS

    Some members are announced only when what they describe exists, and are absent otherwise rather than empty:

    Members Present when
    registration_endpoint The registration policy of the tenant registers clients. Closed, which is the default, the tenant has no registration endpoint at all. Dynamic registration
    backchannel_authentication_endpoint, backchannel_token_delivery_modes_supported, backchannel_authentication_request_signing_alg_values_supported, backchannel_user_code_parameter_supported A grant of the backchannel flow is wired; the last one is then false. Backchannel authentication
    authorization_signing_alg_values_supported, authorization_encryption_alg_values_supported, authorization_encryption_enc_values_supported A signed response mode is wired
    mtls_endpoint_aliases mutual_tls.origin names the host that asks for a certificate
    protected_resources A client of the tenant registered resources (RFC 9728 §4). Resources
    authorization_details_types_supported A type of authorization detail is wired (RFC 9396 §10). Authorization details

    The document announces no check_session_iframe: OpenID Connect Session Management 1.0 is not implemented, and logout goes through the front and back channels. Its content changes when the wiring or the registrations of the tenant change, never during a key rotation, which is the JWK Set's business.

    The JWK Set¶

    GET /jwks, the jwks_uri of the discovery document, answers 200 with application/json and the public keys of the tenant (RFC 7517 §5).

    What it holds. Every key of the tenant in service, staged, active or retiring, of an algorithm the tenant publishes for: the keys it signs with and the keys a client encrypts to it with. Each JWK carries its kid, kty, alg and use, and nothing private. The keys the tenant keeps for itself are never in it, whatever their status: the key a browser is handed for web push, the key the tenant seals what leaves the process to, and the SAML keys, whose certificates the SAML metadata publish.

    How long a client keeps it. The answer says Cache-Control: public, max-age= followed by keys.jwks_max_age, three hundred seconds by default. A set with no key in it is answered no-store, so that no cache keeps an empty set for that long.

    config/packages/beffroi.yaml
    beffroi:
    keys:
        # kms and key_id, as the deployment names them
        jwks_max_age: 300
    Option Default What it decides
    jwks_max_age 300 The max-age of the JWK Set, in seconds. The max-age of the SAML metadata reads it too
    staging_delay jwks_max_age plus 60 How long a new key is published before it signs, in seconds, for every key but the SAML signing key, which has its own

    Through a rotation¶

    A rotation asks a client for nothing but to read the set again within its max-age.

    1. A new key is published before it signs, for staging_delay seconds: three hundred and sixty by default, the max-age of the set plus the sixty seconds a copy has to be old before Symfony's oidc_login fetches the set again on a kid it does not know. A client with a warm cache has seen the new key by the time anything is signed with it.
    2. The new key becomes active once that delay has run, and signs from then on; the key it replaces is retiring, and stays in the set.
    3. The retiring key leaves the set once nothing it signed can still be presented: the longest lifetime among the ID token, the at+jwt when a client of the tenant receives that shape, the logout token up to its exp, which is the budget of its delivery, and the signed authorization response when a signed mode is wired. A key a client encrypts to stays as long as a pushed request or a request object encrypted to it may still arrive. The timed step retires it past that date.

    An operator can cut the first step short, and a client with a warm cache then meets a kid it does not know yet: a key activated before its delay has run, with beffroi:keys:activate, a key that takes over at once, with beffroi:keys:rotate --now, and a key that replaces a compromised one, with --compromised, after which the compromised key leaves the set at once, with no window. Keys gives the commands that rotate, activate and retire a key, and the timed step that stages a successor once a key has worked its age.
